# Библиотека Go для добавления схемы в SQL-миграции PostgreSQL

Исследование, 1–2 октября 2026. Код и данные лежат в [`poc/`](poc/README.md). Постановка задачи — [TASK.md](TASK.md), текущее состояние — [HANDOFF.md](HANDOFF.md).

## Коротко

**Рекомендация: [`github.com/wasilibs/go-pgquery`](https://github.com/wasilibs/go-pgquery).** Это парсер самого PostgreSQL (libpg_query, грамматика PostgreSQL 17), скомпилированный в WebAssembly и исполняемый рантаймом [wazero](https://wazero.io), который написан на чистом Go. Сборка работает с `CGO_ENABLED=0`. API совпадает с `pg_query_go`.

Почему именно он:
- Грамматика та же, что у сервера, по построению: libpg_query собран из исходников PostgreSQL 17. PL/pgSQL разбирается тем же кодом, что в сервере. Поэтому в замерах ниже он служит эталоном.
- Отдаёт позиции узлов в тексте и токены сканера. Поэтому `schema.` можно вставить в исходный текст точечно, не генерируя SQL заново. Комментарии, форматирование и кавычки остаются как в оригинале.
- Результат проверяется: вывод разбирается повторно, и его дерево сравнивается с ожидаемым. Если не совпало, переписывание отказывает с ошибкой, а не возвращает непроверенный SQL.
- PoC на нём прошёл 22 из 23 сценариев на живом PostgreSQL 16 и все применимые сценарии на PostgreSQL 12–15. Непройденный сценарий — динамический SQL в `EXECUTE`, его не переписывает ни одна библиотека. На регрессионных тестах PostgreSQL 12–16 (32–43 тыс. операторов на версию) отказов 10–11 на версию (0,03%), и ни одного непроверенного результата. Две другие реализации сверены с ним на тех же операторах.

Чем за это платим:
- Холодный старт около 1,5 с: wazero компилирует WASM-модуль при первом вызове. Дальше 90–150 мкс на разбор оператора. Снимается сборкой через wasm2go: [§10](#10-без-wasm-рантайма-wasm2go).
- Бинарник около 15 МБ.
- Небольшой проект: 60 звёзд на GitHub. Но его использует sqlc в сборках без cgo.
- Разбор PL/pgSQL в libpg_query идёт без каталога. Присваивание полю составной переменной PoC обходит. Не разбираются параметры `refcursor`, `$0` в полиморфных функциях и элемент массива как цель `GET DIAGNOSTICS`: на них переписывание отказывает с ошибкой.

WASM-рантайм и холодный старт убираются без смены парсера ([§10](#10-без-wasm-рантайма-wasm2go)). Тот же libpg_query из go-pgquery переводится в обычный Go утилитой [wasm2go](https://github.com/ncruces/wasm2go): в PoC это сборка с тегом `wasm2go`. Ответы побайтно те же, первый вызов около 1 мс вместо 1,4 с, разбор в 2–3,5 раза быстрее. Цена — 6,9 МБ сгенерированного кода и около 1,2 ГБ памяти компилятора на этот пакет (с флагами 0,7–0,8 ГБ).

Если переписывание нужно в десятках сервисов, парсер в них лучше не встраивать ([§11](#11-десятки-сервисов-переписывание-при-сборке)). Миграции переписываются при сборке с меткой вместо схемы, а сервис только подставляет имя схемы. Результат побайтно совпадает с прямым переписыванием.

Запасные варианты, если WASM неприемлем:
- **ANTLR-грамматика [bytebase](https://github.com/bytebase/parser)**. Тоже правка токенов, прошёл 21 из 23 сценариев. Где грамматика разобрала SQL, текст совпал с go-pgquery байт в байт. Главный минус — грамматика отстаёт от PostgreSQL. На регрессионных тестах PostgreSQL 16 она не разбирает 1,1% операторов, в том числе `MERGE`, `CREATE OR REPLACE TRIGGER`, тело функции `RETURN`, `COMPRESSION`. Есть и ошибки разбора: `ALTER TABLE t ADD CONSTRAINT c CHECK (…)` разбирается как добавление колонки `CONSTRAINT` типа `c`, `FROM unnest((SELECT …))` — как таблица `unnest`. Ещё минусы: в 5–13 раз медленнее go-pgquery, код переписывания привязан к правилам грамматики, нужен `replace` на форк рантайма ANTLR.
- **[multigres](https://github.com/multigres/multigres)** — порт грамматики PostgreSQL на чистый Go, самый быстрый. Но позиций имён нет, поэтому SQL приходится генерировать заново (deparse). Это теряет комментарии и форматирование. Кроме того, deparse молча менял смысл: `INITIALLY DEFERRED` → `INITIALLY IMMEDIATE`, терял `NO INHERIT` и `RECURSIVE`. Для генерации миграций сейчас не годится.

Не подходят: cockroachdb-parser (другой диалект), pgplex/pgparser (нет позиций и генерации SQL), остальные — см. [обзор](#3-обзор-библиотек).

## 1. Задача

Миграции накатываются golang-migrate через pgbouncer в transaction mode. `search_path` там не задать. Нужен механизм, который по флагу и имени схемы добавляет схему к объектам в SQL-файлах:

```sql
CREATE TABLE users (...)       -- было
CREATE TABLE auth.users (...)  -- стало
```

Цель исследования — выбрать библиотеку для разбора и изменения SQL. Встраивание в golang-migrate — вне скоупа.

Уточнённые требования:
- квалифицировать таблицы и индексы в DDL, таблицы в DML, прочие объекты (последовательности, типы, представления, функции, триггеры) и SQL внутри тел функций и DO-блоков (`$$…$$`);
- только pure Go: CGO запрещён;
- результат: отчёт и PoC на 2–3 библиотеках с общим набором SQL-сценариев.

## 2. Критерии

| Критерий | Почему важен |
|---|---|
| Полнота грамматики PostgreSQL, включая PL/pgSQL | Иначе часть миграций не разберётся или будет переписана неверно |
| Позиции узлов в тексте | Позволяют вставить `schema.` точечно и не генерировать SQL заново |
| Качество генерации SQL (deparse), если позиций нет | Ошибка deparse незаметно меняет смысл миграции |
| Pure Go | Требование: сборка с `CGO_ENABLED=0` |
| Зрелость и поддержка | Библиотека попадает в путь выкатки схемы |
| Скорость и размер | Для миграций вторично, но холодный старт заметен в CLI |

## 4. PoC

Три реализации одного и того же переписывания: [`poc/pgquery`](poc/pgquery), [`poc/multigres`](poc/multigres), [`poc/antlr`](poc/antlr). Правила квалификации общие.

### 4.1 Правила квалификации

| Что | Правило |
|---|---|
| Имя создаваемого, изменяемого или удаляемого объекта (`CREATE`, `ALTER`, `DROP`, `COMMENT ON`, `GRANT ON`) | квалифицируется всегда |
| Ссылка на таблицу, представление, последовательность, индекс | квалифицируется, кроме имён CTE в области видимости, временных таблиц, transition tables триггеров (`REFERENCING NEW TABLE AS x`), `pg_*`, `FOR UPDATE OF x` и явного списка исключений |
| Ссылка на тип или функцию | только если объект создан миграциями. Встроенные объекты и объекты расширений (`gen_random_uuid`, `crypt`, `citext`) не трогаются |
| Строка с именем отношения | `nextval('s')`, `currval`, `setval`, `pg_get_serial_sequence('t', …)`, `to_regclass`, `'t'::regclass`, `'t'::regtype` — схема добавляется внутрь литерала |
| Тела функций `LANGUAGE sql` и `plpgsql`, DO-блоки | встроенный SQL переписывается по тем же правилам, включая `%TYPE` и `%ROWTYPE` в `DECLARE` |
| Динамический SQL (`EXECUTE '…'`, `format(…)`) | не переписывается, выдаётся предупреждение |
| Поиск в каталогах по имени, `current_schema()`, `SET search_path`, `CREATE EXTENSION` без `SCHEMA`, классы и семейства операторов | предупреждение |

Типы и функции из прошлых миграций нужно знать заранее. Для этого у переписывающего есть `Learn(sql)`: стенд вызывает его для всех up-файлов перед переписыванием. golang-migrate тоже может прочитать все файлы источника заранее.

### 4.2 Корпус

23 сценария в формате golang-migrate (up и down) в [`poc/corpus`](poc/corpus). Покрыты: таблицы, FK и индексы; ALTER, RENAME, COMMENT ON; последовательности и regclass-литералы; enum, domain, composite; представления и матпредставления; DML с JOIN, ON CONFLICT, UPDATE … FROM, DELETE … USING, FOR UPDATE OF; CTE с затенением имён таблиц; SQL-функции (в `$$`, в `'…'`, стандартное тело `RETURN` и `BEGIN ATOMIC`); PL/pgSQL (триггеры, курсоры, PERFORM, RETURN QUERY); DO-блоки; динамический SQL; партиции и наследование; GRANT и RLS; кавычки и зарезервированные слова; расширения, системные каталоги, temp-таблицы; STATISTICS (включая `SET STATISTICS`), RULE, CLUSTER; `CREATE INDEX CONCURRENTLY`; transition tables, INSTEAD OF, constraint trigger; имена таблиц внутри строк и комментариев; объекты из прошлых миграций.

Сценарий может указать минимальную версию сервера (`min_server_version` в `case.json`). Синтаксис новее PostgreSQL 12 вынесен в отдельные сценарии: 22 (`RETURN`, `BEGIN ATOMIC`, нужен PostgreSQL 14) и 23 (`ALTER STATISTICS … SET STATISTICS`, нужен PostgreSQL 13). Остальные сценарии идут на всех версиях.

### 4.3 Стенд

[`poc/harness`](poc/harness) поднимает временный PostgreSQL (проверены 12–16) и для каждого сценария и каждой реализации:
1. переписывает файлы;
2. накатывает up-миграции с `search_path = trap, public`: схемы `auth` в пути нет, как за pgbouncer;
3. сравнивает `pg_dump --schema-only` схемы `auth` с эталоном — оригинальным SQL, выполненным с `search_path = auth`;
4. выполняет проверки: вставки, вызовы функций, срабатывание триггеров;
5. ищет объекты, созданные вне `auth`;
6. откатывает down-миграции и проверяет, что `auth` пуста.

Корпус проверен в обе стороны на каждой версии. Оригинал с `search_path = auth` проходит все сценарии. Оригинал без переписывания и без схемы в пути падает во всех сценариях.

Что нашёл стенд:
- **multigres, сценарий 19.** Deparse превратил `CREATE CONSTRAINT TRIGGER … DEFERRABLE INITIALLY DEFERRED` в `INITIALLY IMMEDIATE`. Миграция выполнилась без ошибок, триггер работал, а схема отличалась от эталона. Это поймало только сравнение `pg_dump`.
- **Все три первых версии.** Имя в `FOR UPDATE OF r` квалифицировалось, и PostgreSQL отвечал `FOR UPDATE must specify unqualified relation names`. Исправлено, сценарий добавлен в корпус.
- **go-pgquery.** libpg_query не разбирал присваивание полю переменной `%ROWTYPE` (`w.balance := …`). В PoC добавлен обход, сценарий 10 дополнен. Позже нашлось, что обход не срабатывал для уже квалифицированного `other.t%ROWTYPE`: исправлено, добавлен тест.
- **multigres.** Его AST в части мест отличается от дерева PostgreSQL: например, `DROP TRIGGER t ON tbl` хранится плоским списком. Код под одну библиотеку не переносится на другую без отладки.
- **ANTLR, сценарий 22.** Грамматика bytebase не знает стандартное тело SQL-функции `RETURN выражение` (PostgreSQL 14+): в ней есть только `BEGIN ATOMIC`. Переписывание отказывает с синтаксической ошибкой.
- Корпус ловил и мои регрессии при доработке. Например, неудачная правка обработки `RENAME` сломала сценарий 21: новое имя типа перестало попадать в реестр.

На PostgreSQL 12 пропущены сценарии 22 и 23, на 13 — сценарий 22.

Итог: от версии сервера результат не зависит. Падения одни и те же на всех версиях: сценарий 12 у всех (динамический SQL), 19 у multigres (deparse), 22 у ANTLR (грамматика). go-pgquery и ANTLR только вставляют схему и не меняют остальной текст, поэтому их вывод выполняется на тех же версиях, что и исходник. multigres генерирует SQL заново. На корпусе его вывод выполнился на всех версиях. Предположение: на другом SQL генератор может выдать синтаксис новее сервера.

Что понадобилось для старых версий:
- `BEGIN ATOMIC` вынесен из сценария 08 в новый 22, `ALTER STATISTICS … SET STATISTICS` — из 17 в новый 23.
- Сценарий 01 на PostgreSQL 12 ставит pgcrypto ради `gen_random_uuid()`: она встроена только с 13.
- Стенд не использует `DROP DATABASE … WITH (FORCE)` на PostgreSQL 12: эта форма появилась в 13.

Расхождения ANTLR (112):
- 49 — классы и семейства операторов. go-pgquery их не переписывает и выдаёт предупреждение. ANTLR-PoC квалифицирует и встроенные функции поддержки: `FUNCTION 1 btint42cmp(int4, int2)` → `auth.btint42cmp`.
- 37 — объекты, которые ANTLR-PoC не покрывает, а go-pgquery квалифицирует: `TEXT SEARCH` (12), `CONVERSION` (11), таблицы в публикациях (6), `nextval('s'::text)` и подобные (6), тип строки сторонней таблицы (1), функция `unbounded()` в рамке окна (1).
- 25 — ошибки ANTLR:
  - `FROM unnest((SELECT …))` грамматика разбирает как таблицу `unnest` (11);
  - функции с телом `RETURN` грамматика не разобрала, поэтому они не попали в реестр, и их вызовы остались без схемы (8);
  - temp-представления с `SEARCH`/`CYCLE` не распознаны как временные и получили схему (3);
  - самоссылка в `CREATE RECURSIVE VIEW` получила схему (2);
  - встроенные функции в `CREATE TRANSFORM` получили схему (1).
- 1 — `RETURN QUERY SELECT … INTO t` в PL/pgSQL: go-pgquery квалифицирует `t`, ANTLR нет. Этот оператор падает в PostgreSQL в обоих вариантах.

Расхождения multigres (3 987):
- 3 065 — deparse меняет дерево самого исходного оператора, без всякого переписывания.
- 784 — тела функций и DO-блоки. multigres генерирует текст тела заново, а в дереве тело хранится строкой. В 747 из них схему получили те же имена, что у go-pgquery.
- 138 — разные правила для редких объектов. multigres-PoC не квалифицирует `TEXT SEARCH` (81), `CONVERSION` (26), `COLLATION` (9), `STATISTICS` (5), домены в `RENAME CONSTRAINT` и `COMMENT ON CONSTRAINT` (2), а имена операторов в `DROP OPERATOR` квалифицирует (15). go-pgquery — наоборот.
- 10 отказов: deparse выдал SQL, который не разбирается (5, из них 3 — `COMMENT ON RULE`); PL/pgSQL-парсер не принял циклы по курсору (3); лексер не принял `$1a` (2).

Сверка нашла и пробел в go-pgquery-PoC: домен в `COMMENT ON CONSTRAINT c ON DOMAIN d` получал схему, только если его создали миграции. Исправлено, добавлен тест.

Итог сверки. На PostgreSQL 16 две реализации на разных парсерах совпали байт в байт на 98,70% операторов. Почти всё остальное ANTLR не разобрал. Среди расхождений — редкие объекты (классы операторов, полнотекстовый поиск, конверсии), которые PoC покрывают по-разному, и ошибки ANTLR. Предположение: в миграциях приложений такие объекты редки.

### 5.4 Скорость и размер

Замер в одном процессе, без фоновой нагрузки, 4 ядра. Для повторных прогонов взята медиана из 15.

| | go-pgquery | multigres | bytebase ANTLR |
|---|---|---|---|
| Первый вызов | ~1,45 с (компиляция WASM) | ~0 | 15–150 мс, зависит от оператора |
| Все 27 up-файлов корпуса, первый прогон в процессе | ~1,5 с | ~0,02 с | ~1,5 с |
| То же, повторный прогон | ~0,11 с | ~0,013 с | ~0,53 с |
| Файл с PL/pgSQL (2,2 КБ), прогретый процесс | ~14 мс | ~1 мс | ~70 мс |
| Размер CLI (`CGO_ENABLED=0`, linux/amd64) | 15 МБ | 12 МБ | 23 МБ |
| Минимальная версия Go у библиотеки | 1.25 | 1.26 (ветка main) | 1.24 |
| Код PoC без тестов | ~1 950 строк | ~910 строк | ~790 строк |

У ANTLR первый вызов быстрый, но кэш предсказаний (DFA) наполняется по ходу работы. Поэтому первый прогон корпуса почти втрое дольше повторного. ANTLR отказывает на сценарии 22, его время в замере тоже учтено.

Для миграций любой вариант укладывается в секунды. Код go-pgquery-PoC самый большой: поиск имён без позиций в токенах, проверка по дереву и обходы для PL/pgSQL.

## 6. Кандидаты подробно

### go-pgquery (рекомендую)

Плюсы:
- Грамматика сервера по построению: libpg_query собран из исходников PostgreSQL 17.7.
- Позиции узлов и сканер токенов позволяют править текст точечно. Diff миграции после переписывания — только вставки `auth.`.
- Собственный deparse libpg_query почти без расхождений (99,99%). Если когда-нибудь понадобится генерировать SQL, он есть.
- Разбор PL/pgSQL возвращает каждое встроенное SQL-выражение с номером строки.
- API совместим с `pg_query_go`. Если CGO когда-нибудь разрешат, замена — одна строка импорта или тег сборки `pgquery_cgo`.
- Используется в [sqlc](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/engine/postgresql/parse_wasi.go) в сборках без cgo и под Windows.

Минусы:
- WASM: старт около 1,5 с. По замеру автора библиотеки разбор в 4–5 раз медленнее cgo-версии ([README](https://github.com/wasilibs/go-pgquery#performance)). Кэш компиляции wazero библиотека наружу не отдаёт. Оба минуса снимает сборка через wasm2go ([§10](#10-без-wasm-рантайма-wasm2go)).
- Малый проект: 60 звёзд. Риск — задержка обновлений под новые версии PostgreSQL. Смягчение: тот же API у `pg_query_go` от pganalyze.
- Для части имён позиций нет. Это имена в `DROP`, `COMMENT ON`, `CREATE FUNCTION`, `CREATE TYPE`, `EXECUTE FUNCTION` триггера. Их приходится искать сканером в токенах оператора. Ошибку поиска ловит проверка дерева.
- PL/pgSQL разбирается без каталога, поэтому составными libpg_query считает только типы вида `схема.тип`. Присваивание полю составной переменной или параметра PoC обходит: для разбора такие объявления подменяются на `record`, а типы параметров квалифицируются. Не обходятся параметры `refcursor`, `$0` в полиморфных функциях и элемент массива как цель `GET DIAGNOSTICS`: переписывание отказывает с ошибкой.

### bytebase ANTLR (запасной вариант без WASM)

Плюсы:
- Чистый Go без WASM. Токены точные, `TokenStreamRewriter` сохраняет комментарии и форматирование.
- Тела функций разбираются той же грамматикой.
- Где грамматика разобрала SQL, результат почти всегда совпал с go-pgquery байт в байт: на корпусе во всех таких сценариях, на регрессионных тестах PostgreSQL 16 — в 98,70% операторов. Остальное в основном отказы грамматики.

Минусы:
- Медленно: разбор ~1,5 мс на оператор против ~0,12 мс у go-pgquery. Переписывание в прогретом процессе примерно в 5 раз медленнее go-pgquery. Первый прогон корпуса — около 1,5 с, как у go-pgquery.
- Дерево конкретного синтаксиса: смысл имени зависит от родительского правила. В PoC это 20 обработчиков и 36 веток по родительскому правилу. Их нужно сверять с грамматикой при каждом обновлении.
- Проверки по дереву, как у go-pgquery, нет: свой AST для сравнения отсутствует.
- `go.mod` библиотеки требует `replace github.com/antlr4-go/antlr/v4 => github.com/bytebase/antlr/v4`, и его приходится повторять у себя.
- Грамматика отстаёт от PostgreSQL. На регрессионных тестах она не разбирает 0,35% операторов PostgreSQL 12 (в основном XML-функции) и 1,07% PostgreSQL 16. Среди неразобранного есть и то, что встречается в миграциях: `MERGE`, `CREATE OR REPLACE TRIGGER`, тело функции `RETURN`, `COMPRESSION`, `STORAGE` у колонки, `DETACH PARTITION … CONCURRENTLY`, `GRANTED BY` (§5.3). На такой миграции переписывание отказывает.
- Ошибки грамматики, которые не видны снаружи. `ALTER TABLE t ADD CONSTRAINT c CHECK (…)` разбирается как добавление колонки с именем `CONSTRAINT` и типом `c`. Если в миграциях есть тип или таблица с именем `c`, переписывание квалифицирует имя ограничения. В PoC стоит заплатка. `FROM unnest((SELECT …))` разбирается как таблица `unnest`, и PoC добавляет ей схему. Тело функции в одинарных кавычках разбирается без последнего символа; в PoC тело разбирается отдельно. `PERFORM FROM …` в PL/pgSQL не разбирается вовсе.
- Сверка с go-pgquery на регрессионных тестах нашла в ANTLR-PoC ошибки: `REINDEX SCHEMA x` превращалось в `auth.x`; temp-таблица в `CREATE TEMP TABLE … AS EXECUTE` получала схему; имена в `SET CONSTRAINTS` не квалифицировались. Эти исправлены, но каждая — отдельное правило грамматики, которое нужно знать. Не исправлены: самоссылка в `CREATE RECURSIVE VIEW` и встроенные функции в классах операторов получают схему (§5.3).
- Репозиторий малоизвестен (11 звёзд), хотя грамматика используется в продукте Bytebase.

### multigres (следить, пока не использовать)

Плюсы:
- Чистый Go, очень быстрый: ~7 мкс на оператор.
- Разбирает почти все регрессионные тесты PostgreSQL 12–16: на 16-й не принял 2 оператора из 42 798. В ветке main есть разбор PL/pgSQL с deparse.
- Активная разработка, 2,7 тыс. звёзд у проекта.

Минусы:
- Позиций имён нет, поэтому весь файл генерируется заново. Комментарии теряются, форматирование, регистр и кавычки меняются, `SELECT … INTO x FROM` превращается в `SELECT … FROM … INTO x`.
- Deparse меняет дерево у ~7% операторов на любой версии. Большинство случаев эквивалентны (`::float4` → `CAST(… AS REAL)`), но есть и смена смысла: `INITIALLY DEFERRED` → `IMMEDIATE`, потеря `NO INHERIT` у CHECK, `CREATE RECURSIVE VIEW` → `CREATE VIEW`. Для `COMMENT ON RULE r ON t` deparse выдал SQL, который не разбирается.
- Парсер — пакет внутри приложения multigres, а не отдельная библиотека. Проект сам пишет о себе «early stages of development». Разбор PL/pgSQL есть только в main, ветке нужен Go 1.26.
- AST местами расходится с деревом PostgreSQL.

### Отсеянные

- **pgplex/pgparser**: грамматика полная, но позиций нет, а deparse нет. Для переписывания пришлось бы писать свой генератор SQL.
- **cockroachdb-parser**: разбирает 76–78% регрессионных тестов PostgreSQL 12–16, на 16-й 64 раза падает с panic (в том числе на DO-блоках), не знает `CREATE DOMAIN` и `COMMENT ON FUNCTION`. Генерирует SQL в диалекте CockroachDB: `int` → `INT8` (в PostgreSQL это уже bigint), `text` → `STRING`.
- Остальные не являются полными парсерами PostgreSQL или заброшены.

## 7. Ограничения подхода

Они не зависят от библиотеки.

1. **Динамический SQL.** `EXECUTE 'INSERT INTO t …'` и `format('%I', …)` статически не переписать. Решение — договорённость: в динамическом SQL писать схему явно. Переписывание выдаёт предупреждение.
2. **Поиск по каталогам по имени.** `WHERE typname = 'x'` без условия на схему найдёт одноимённый объект в другой схеме. `current_schema()` за pgbouncer вернёт не целевую схему. Переписывание выдаёт предупреждение, исправлять вручную.
3. **Объекты других схем без схемы в имени.** Если миграция намеренно обращается к `public.countries` как к `countries`, ссылка станет `auth.countries` и упадёт с ошибкой. Ошибка шумная, не тихая. Решение — список исключений `ExcludeRelations`.
4. **Типы и функции распознаются по имени.** Своя функция `lower(my_type)` сделает квалифицированными все вызовы `lower`. Встречается редко.
5. **`CREATE EXTENSION` без `SCHEMA`** создаёт объекты в первой схеме `search_path`. Переписывание это не меняет и выдаёт предупреждение.

## 8. Что дальше

1. Прогнать `poc/pgquery/cmd/pgschema-rewrite` на реальных миграциях. Посмотреть на отказы и предупреждения.
2. Добавить реальные миграции в корпус и гонять стенд в CI.
3. Встраивание (вне этого исследования): естественная точка — обёртка над `source.Driver` golang-migrate, которая переписывает `ReadUp` и `ReadDown`, а при открытии вызывает `Learn` для всех up-файлов.
4. Выбрать схему для сервисов ([§11](#11-десятки-сервисов-переписывание-при-сборке)): переписывание при сборке с меткой или общий образ мигратора. Для первого нужны режим метки в `pgschema-rewrite` и подстановщик в обёртке `source.Driver`.
5. Предложить авторам go-pgquery сборку через wasm2go ([§10](#10-без-wasm-рантайма-wasm2go)). Тогда сборочный конвейер не придётся поддерживать у себя.

## 9. Вне скоупа

postgres-драйвер golang-migrate v4.20.1 берёт блокировку через `pg_advisory_lock` и снимает через `pg_advisory_unlock` ([`database/postgres/postgres.go`](https://github.com/golang-migrate/migrate/blob/v4.20.1/database/postgres/postgres.go)). Это блокировки уровня сессии. За pgbouncer в transaction mode захват и снятие могут уйти в разные серверные соединения. Схему для таблицы `schema_migrations` драйвер берёт из `SELECT CURRENT_SCHEMA()`. Стоит проверить до внедрения.

## 10. Без WASM-рантайма: wasm2go

Холодный старт go-pgquery — это не разбор, а компиляция WASM-модуля (2,5 МБ) рантаймом wazero при первом вызове. Тот же модуль можно заранее перевести в обычный Go утилитой [wasm2go](https://github.com/ncruces/wasm2go). Через неё же собирается go-re2 из той же организации wasilibs. В рантайме тогда нет ни WASM, ни wazero: работает скомпилированный Go-код, который зависит только от стандартной библиотеки. CGO не нужен.

В PoC это сборка с тегом `wasm2go`:
- [`poc/pgquery/wasm2go/build.sh`](poc/pgquery/wasm2go/build.sh) генерирует [`poc/pgquery/internal/libpgquery`](poc/pgquery/internal/libpgquery) из C-исходников libpg_query, которые лежат в go-pgquery (версия из `go.mod`). Нужны wasi-sdk 34, binaryen 133 и wasm2go v0.4.16, скрипт скачивает их сам. Результат детерминирован: повторный запуск даёт те же байты.
- `internal/pgparse` выбирает бэкенд: по умолчанию go-pgquery, с `-tags wasm2go` — `internal/libpgquery`. Код переписывания не меняется.

Чем сборка отличается от сборки go-pgquery:
- без потоков (`wasm32-wasip1`);
- `setjmp`/`longjmp` в стиле Emscripten вместо WASM-исключений: `longjmp` становится panic, которую ловит обёртка `invoke_*`;
- экспортированы только разбор, сканер и разбор PL/pgSQL;
- действия грамматики `base_yyparse` разнесены по 16 функциям ([`split_gram.py`](poc/pgquery/wasm2go/split_gram.py)), wasm-opt запущен с `-g`. Зачем — ниже, в разделе про сборку.

### 10.3 Сборка

Сгенерированный пакет — 6,9 МБ Go-кода, 115 тыс. строк. Компилятору Go на большую функцию нужно непропорционально много памяти. Первая версия без разрезания брала 2,6–2,8 ГБ и 30 с на пакет. Причина — две функции по ~21 тыс. строк: `switch` с 2 271 действием грамматики SQL и функция, которую wasm-opt собрал встраиванием из десятков других. С заглушками вместо них пик падал до 0,8 ГБ. Уровни оптимизации C и wasm-opt (`-Os`, `-Oz`, без wasm-opt) давали 2,3–2,8 ГБ. Разрезание действий и `-g` у wasm-opt уменьшили самую большую функцию до 4 тыс. строк. Скорость и результат не изменились.

Память компилятора на этот пакет, замер [`wasm2go/maxrss`](poc/pgquery/wasm2go/maxrss/main.go):

| Флаги | Пик | Время |
|---|---|---|
| по умолчанию | 1,16–1,27 ГБ | 9–10 с |
| `GOMAXPROCS=2` | 1,12 ГБ | 13 с |
| `-gcflags=<пакет>=-c=1`, `GOGC=50` | 0,82 ГБ | 14 с |
| `-gcflags=<пакет>=-c=1`, `GOMEMLIMIT=500MiB` | 0,66 ГБ | 20 с |

`-c=1` заставляет компилятор обрабатывать функции пакета по одной. Флаг действует только на указанный пакет и задаётся и через `GOFLAGS`.

Чистая сборка всего CLI вместе со стандартной библиотекой под жёстким лимитом памяти. Лимит задан через cgroup, в него входит и кэш страниц.

| Лимит | Сборка | Результат |
|---|---|---|
| 1,5 ГБ | wasm2go, флаги по умолчанию | собирается, 16 с |
| 1 ГБ | wasm2go, флаги по умолчанию | компилятор убит по OOM |
| 1 ГБ | wasm2go, `-c=1`, `GOGC=50` | собирается, 22 с |
| 768 МБ | wasm2go, `-c=1`, `GOMEMLIMIT=500MiB`, `-p 1` | собирается, 32 с |
| 640 МБ | wasm2go, `-c=1`, `GOMEMLIMIT=450MiB`, `-p 1` | не собирается |
| 512 МБ | go-pgquery, флаги по умолчанию | собирается, 12 с |

Ещё:
- с прогретым кэшем Go пакет заново не компилируется: пересборка после правки переписывателя — 0,6 с и 84 МБ;
- сборка CLI, когда в кэше только стандартная библиотека: wasm2go +11 с на 4 ядрах и +15 с на 2 ядрах, go-pgquery +6 и +10 с;
- `go vet` пакета — около 0,4 ГБ, сборка с `-race` — 0,47 ГБ, с `-cover` — 1,73 ГБ. Пакет лучше исключить из покрытия.

### 10.4 Минусы

- Сгенерированный код нечитаем. С `-g` в стеке panic видны имена C-функций (`_pg_query_raw_parse_plpgsql`).
- wasm2go — молодой проект (v0.4). Им собираются go-sqlite3 и go-re2. Нужен только для генерации: сгенерированный код зависит лишь от стандартной библиотеки.
- Генератору нужен Go 1.26. Сгенерированный код собирается Go 1.24 и 1.25, кросс-сборка под darwin/arm64 и windows/amd64 проходит.
- Сборочный конвейер (wasi-sdk, binaryen, патчи) — наш, пока go-pgquery сам не перейдёт на wasm2go.
- Срабатывание assert в C-коде — это panic. Обёртка превращает её в ошибку и выбрасывает экземпляр модуля. go-pgquery в таком случае паникует: например, `ParsePlPgSqlToJSON` на SQL-функции с телом `RETURN`. Переписыватель такие функции туда не передаёт.

### 10.5 Другие варианты

- Кэш компиляции wazero на диске. Первый запуск — 1,55 с, следующие — около 0,26 с, кэш занимает 14 МБ. go-pgquery кэш не включает, нужен форк. В CI с чистым контейнером каждый запуск снова холодный.
- Интерпретатор wazero. Старт 0,15 с, но разбор примерно в 25 раз медленнее: 2,8 мс на `CREATE TABLE`.
- Свой парсер на чистом Go. pgplex/pgparser (порт gram.y PostgreSQL 17) позиций не даёт: у всех узлов `Location` равен 0 или −1, проверено на ветке main. PL/pgSQL у него нет, дерево местами расходится с PostgreSQL. В gram.y PostgreSQL 17 — 19 520 строк и 727 правил, позиции задаются в 625 местах; PL/pgSQL — ещё 4 172 строки `pl_gram.y`. Оценка доработки pgplex — 2–3,5 месяца, парсера с нуля — 4–6 месяцев (прогноз). Грамматика при этом перестаёт совпадать с серверной по построению.

## 11. Десятки сервисов: переписывание при сборке

Если переписыватель встроен в каждый сервис, за это платит каждый сервис:
- сборка: +6–15 с при каждом промахе кэша, для wasm2go ещё 1–1,5 ГБ памяти в пайплайне ([§10.3](#103-сборка));
- старт и память процесса: у go-pgquery 1,5 с и 287 МБ на пике;
- обновление libpg_query — правка в десятках репозиториев.

Результат переписывания зависит только от файлов миграций и имени схемы. Поэтому переписать можно один раз при сборке, а в сервисе оставить подстановку:
1. Утилита переписывает миграции с меткой вместо схемы: `pgschema_placeholder.users`.
2. Сервис при чтении файла заменяет метку на имя схемы через `strings.ReplaceAll`. Хватает стандартной библиотеки.
3. Если флаг выключен, сервис берёт исходные файлы.

[`TestPlaceholder`](poc/pgquery/placeholder_test.go) проверяет, что метка и замена дают тот же текст, что прямое переписывание. Входы: файлы корпуса (up и down) и 43 323 оператора регрессионных тестов PostgreSQL 16. Схемы: `auth`, `Auth`, `user` (ключевое слово) и `my schema`. Для каждой схемы совпали все 42 841 текст, 24 915 из них переписывание изменило. Отказы одинаковые (536), расхождений 0.

Ограничение: в имени схемы не должно быть `'` и `$`. Метка стоит и внутри строковых литералов (`nextval('…')`), и внутри тел функций в долларовых кавычках. Подстановщик должен отвергать такие имена.

Где переписывать:
- Переписанные файлы коммитятся рядом с исходными. CI перегенерирует их и проверяет `git diff`. Плюс: в ревью видно, какие имена получили схему.
- Или файлы генерируются при сборке образа готовым бинарником утилиты, например `COPY --from` из её образа. Плюс: в репозитории ничего лишнего.

Альтернатива — общий образ мигратора: golang-migrate и переписыватель, собранные один раз. Сервисы накатывают миграции отдельным шагом: Job, init-контейнер или шаг деплоя.

Если переписыватель всё же встраивается в сервисы:
- общий образ для сборки с прогретым `GOCACHE`. Проверено: другой модуль с тем же кэшем не стал компилировать пакет заново, сборка заняла 0,76 с. Нужны те же версии Go и библиотеки и те же флаги;
- общий удалённый кэш через `GOCACHEPROG` (Go 1.24+).
