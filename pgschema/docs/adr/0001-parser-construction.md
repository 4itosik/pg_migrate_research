# 0001. Парсер: порт `gram.y` PostgreSQL 17 на goyacc с позициями

Статус: принято, этап 0.

## Контекст

Нужен разбор SQL, который принимает и отвергает те же операторы, что сервер, и отдаёт то же дерево с теми же позициями. Эталон — libpg_query (грамматика PostgreSQL 17). Ограничения: чистый Go, без кода, переведённого из C, разбор оператора в среднем не дольше 20 мкс, пиковая память компилятора на любой пакет не больше 700 МБ.

Рассмотрены два пути: рукописный рекурсивный спуск и порт `gram.y` (19 520 строк, 727 правил) на goyacc.

## Решение

Порт `gram.y` ветки `REL_17_STABLE` на goyacc. Правила и приоритеты берутся из `gram.y` как есть, действия пишутся на Go вручную. Файл грамматики сохраняет заголовок с лицензией PostgreSQL.

Что нужно сверх штатного goyacc, и поэтому он копируется в `internal/tools/goyacc` (BSD-3, авторские права Go сохраняются) и дорабатывается:
1. Позиции. `@N` — позиция символа, `@$` — позиция результата. Позиция лежит в `yySymType.loc`. Правило `YYLLOC_DEFAULT` из PostgreSQL: у правой части из N > 0 символов позиция первого символа (штатное копирование `yyVAL = yyS[yyp+1]` делает это само), у пустой правой части — `-1`. Это не «первый непустой символ»: PostgreSQL берёт первый символ даже с позицией `-1`, и деревья сверяются с libpg_query.
2. Действия выносятся в отдельные функции, см. [0004](0004-small-functions.md).

Однотокенный просмотр вперёд из `parser.c` (`base_yylex`) живёт в обёртке над лексером:
- `FORMAT` перед `JSON` → `FORMAT_LA`;
- `NOT` перед `BETWEEN`, `IN`, `LIKE`, `ILIKE`, `SIMILAR` → `NOT_LA`;
- `NULLS` перед `FIRST`, `LAST` → `NULLS_LA`;
- `WITH` перед `TIME`, `ORDINALITY` → `WITH_LA`;
- `WITHOUT` перед `TIME` → `WITHOUT_LA`;
- `UIDENT` и `USCONST`, в том числе с `UESCAPE`, раскрываются в обычные идентификатор и строку.

Режимы `RawParseMode` (`MODE_TYPE_NAME`, `MODE_PLPGSQL_EXPR`, `MODE_PLPGSQL_ASSIGN1..3`) работают как в `parser.c`: лексер отдаёт токен режима первым. Они нужны для встроенного SQL из PL/pgSQL.

## Обоснование

Замер на настоящей грамматике. `gram.y` превращён скриптом в грамматику без действий (теги типов сведены к одному) и пропущен через штатный goyacc `golang.org/x/tools/cmd/goyacc`:

| | |
|---|---|
| Терминалов, нетерминалов, правил | 539, 728, 3 408 |
| Состояний | 6 457 из 16 000 допустимых |
| Конфликтов | 0 shift/reduce и 0 reduce/reduce, как `%expect 0` в `gram.y` |
| Генерация | 5,8 с |
| Компиляция таблиц разбора | 4,2 с, 135 МБ |

Значит, штатный goyacc грамматику PostgreSQL принимает, лимита состояний хватает с запасом, а таблицы и пустой `yyParse` компилятору не в тягость. Сколько памяти добавят действия, пока неизвестно: этот риск снимает [0004](0004-small-functions.md).

Рукописный спуск отвергнут. Принимаемое множество операторов определяется LALR(1)-разрешением конфликтов в 727 правилах и приоритетами, повторить его вручную без расхождений на 43 тыс. операторов регрессионных тестов — задача на месяцы: исследование (README §10.5) оценивало парсер с нуля в 4–6 месяцев, порт готовой грамматики в 2–3,5 месяца. При порте расхождения ловит сверка. Объём ручной части порта: действий в `gram.y` около 11 100 строк C (строки правил, затронутые фигурными скобками, подсчёт по файлу), плюс около 1 000 строк вспомогательных C-функций в конце файла.

## Последствия

- Ошибки порта — это не принятый или отвергнутый оператор, а расхождение дерева: оно видно сверкой с libpg_query (этап 2).
- Обновление до PostgreSQL 18 — это разность `gram.y` между ветками плюс новые действия, а не новый парсер.
- Сообщения об ошибках у goyacc другие (`syntax error`), с позицией токена. Совпадение текста ошибок с PostgreSQL не требуется; требуется совпадение «принял или отверг».
- Копия goyacc — наш код для сопровождения. Она не входит в зависимости рантайма.

## Проверка

- `goyacc -v`: 0 конфликтов, проверка в тесте генерации.
- Этап 2: деревья вместе с позициями совпадают с libpg_query.
