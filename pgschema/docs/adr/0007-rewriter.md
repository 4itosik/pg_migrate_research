# 0007. Переписывание: вставки по позициям и проверка деревом

Статус: принято, этап 4.

## Контекст

Прототип (`poc/pgquery`) получает позиции имён из дерева libpg_query и, где их нет (список имён в `DROP`, `COMMENT ON`, `CREATE FUNCTION`, `CREATE TYPE`, функция триггера), ищет токены по тексту. Результат проверяет повторным разбором. Библиотека делает то же на своём дереве ([ADR 0002](0002-tree.md)), но позиции у неё есть везде.

## Решение

- Правки — вставки `schema.` по смещениям и замена тела функции целиком; текст вокруг не меняется. Смещение берётся из `Location` узла (`RangeVar`, `TypeName`, `FuncCall`, строковые константы) или из `Loc` узла `String` (наше расширение для имён в списках). Перед вставкой токен по смещению сканируется и сверяется с ожидаемым именем: сдвиг позиции — ошибка, а не тихая правка не там.
- Проверка. Обход вносит те же квалификации в дерево входа (`Schemaname`, лишний `String` в списке имён, новое значение строки). После применения правок результат разбирается заново, и `ast.Equal` сравнивает деревья без позиций (`ast.Diff` описывает первое различие для сообщения). Любое расхождение — ошибка `Rewrite`. Проверка идёт на каждом уровне: тело SQL-функции разбирается как отдельный текст со своей проверкой, фрагмент тела PL/pgSQL — так же, а тело целиком проверяется структурой (те же фрагменты, режимы, объявления, динамические операторы, `verifyBody`).
- Тела. Для PL/pgSQL правила по фрагментам: оператор — как есть; выражение — как `SELECT выражение`; присваивание — выражение после первого `:=` или `=` вне скобок; список `WHEN` у `CASE` — как `x IN (список)`. Правки фрагментов сдвигаются на позицию фрагмента в теле: извлечение отдаёт позиции в декодированном теле, а текст запроса не ищется. Тело в `'…'` или `E'…'` переписывается декодированным и пишется в долларовых кавычках с тегом, которого нет в теле; тело в `$tag$…$tag$` сохраняет тег.
- Реестр: типы, функции, отношения, transition tables, которые создали миграции; наполняется `Learn` по всем up-файлам. Временные таблицы живут только в одном тексте (см. дополнение ниже). Тело, которое нельзя переписать, не оставляет в реестре ничего (журнал и откат внутри `plpgsqlBody`): сервер такую функцию не создал бы.
- Режим метки — `Options{Placeholder: true}`: переписывание с именем схемы `pgschema_placeholder`, которое `subst.Apply` заменяет без парсера. Результат равен прямому переписыванию, потому что кавычки идентификатора решает одна функция (`subst.QuoteIdent`, список слов из `kwlist.h`), а правила квалификации от имени схемы не зависят. Исключение: миграция, которая сама называет целевую схему (`CREATE TABLE auth.users`): шаблон не знает, какая схема целевая, и считает такие имена чужими, а прямое переписывание запоминает объекты (`TestPlaceholderDoesNotKnowTheTargetSchema`). Имена с `'`, `$`, `\` не подставляются: метка стоит и в строках, и в долларовых телах.
- Ошибки парсера (`parse.InternalError`) библиотека возвращает отказом, а не паникой.

## Последствия

- API `Rewrite(sql) (string, []string, error)` и `Learn(sql) error` — как в ориентире промпта; `Options` получил поле `Placeholder`. К v0.1.0 предупреждения стали `[]Warning` (см. дополнение ниже).
- `migratesrc.Wrap(src, schema)` возвращает `source.Driver` без ошибки; недопустимое имя схемы делает ошибкой каждое чтение ([ADR 0005](0005-layout.md)). К v0.1.0 добавлен `migratesrc.New(src, schema) (source.Driver, error)`, который проверяет имя сразу: при `ErrNoChange` чтения нет, и ошибка `Wrap` не видна.
- Проверка деревом ловит сдвиги позиций и неверные квалификации, но не смысл: что имя надо квалифицировать, решают правила. Их проверяют корпус на сервере, регрессионные тесты против прототипа и фаззинг ([PROGRESS](https://github.com/4itosik/pg_migrate_research/blob/claude/sql-parser-schema-golang-55m2uj/pgschema/PROGRESS.md)).

## Дополнение: схема уже указана, расширения

- Имя, у которого схема указана, не меняется; правило одно для всех видов объектов и проверяется тестом на 33 операторах разных видов.
- `CREATE EXTENSION` по умолчанию остаётся как написан (расширение одно на базу, общее для сервисов) и получает предупреждение. `Options.ExtensionsInSchema` дописывает `SCHEMA <схема>` в конец оператора, у которого его нет: места в тексте для вставки после имени нет (у имени расширения в дереве нет позиции), а параметры оператора идут в любом порядке. Проверка деревом сравнивает результат с входным деревом, где к параметрам добавлен `schema`.
- Использование расширений в SQL настраивается по расширению (`Options.Extensions`): имена объектов берутся из таблицы, которую `oracle/cmd/genext` собирает по `pg_depend` живых серверов PostgreSQL 12–16 (без имён, которые есть и в ядре, чтобы не ставить схему расширения на функцию ядра), и из `ExtensionObjects`. Схема, которую получает имя, — отдельная от целевой (`schemaRef`); в шаблоне целевая — метка, остальные — как есть. Операторы расширений не переписываются (синтаксис `OPERATOR(схема.оператор)` оставлен за пределами задачи): на `CREATE EXTENSION` расширения с операторами выдаётся предупреждение.

## Дополнение: решения к v0.1.0

- **Имена встроенных объектов.** Тип или функция миграции с именем типа или функции `pg_catalog` (`CREATE TABLE text`, `CREATE FUNCTION round`) раньше забирали себе каждое использование имени: `name text` становился столбцом составного типа `auth.text`, все вызовы `round` — вызовами `auth.round`, тело функции — бесконечной рекурсией. Теперь использование такого имени без схемы не квалифицируется никогда: `pg_catalog` неявно первая в `search_path`, для типов это и есть разрешение имён PostgreSQL, для функций так сохраняется поведение встроенной. Использование и само создание (оно получает схему, как любое другое) сопровождаются предупреждением: если миграция имеет в виду свой объект, она должна назвать схему явно. Имена — объединение по PostgreSQL 12–16 из `pg_type` и `pg_proc` (функции, агрегаты, процедуры) и ключевые слова типов, которые грамматика отдаёт `pg_catalog` (`int`, `double`, `varchar`, …); их собирает `oracle/cmd/genbuiltins` с живых серверов в `builtins_gen.go`, как `genext` — имена расширений. Имена из `ExtensionObjects` берутся как даны: вызывающий явно назвал их объектами расширения.
- **Область временных таблиц — один текст.** Имя временной таблицы раньше оставалось в реестре навсегда и снимало схему с одноимённой таблицы во всех следующих файлах, включая её `CREATE TABLE`. Теперь оно действует только внутри текста, переданного `Learn` или `Rewrite`, начиная с оператора `CREATE TEMP` (в том числе в телах функций этого текста); `Learn` не переносит его в другие файлы; `CREATE` того же имени без `TEMP` получает схему и снимает подавление для следующих операторов (внутри самого оператора имя ещё означает временную таблицу).
- **Вложенные приведения.** Строка с именем отношения ищется сквозь приведения к `text`, `varchar` и `regclass` (`nextval(('s'::text)::regclass)` старого `pg_dump`), а не через одно.
- **Схема из `CREATE EXTENSION … SCHEMA s` сильнее настройки.** Имена активного расширения указывают на его собственную схему, которую оператор с явной схемой переносит для следующих использований.
- **Состояние и откат.** Каждое изменение состояния `Rewriter` (имена в реестре, включение и перенос расширений) записывается в журнал вместе с функцией отмены; `Learn` и `Rewrite` открывают транзакцию и при ошибке отменяют всё, как тело, которое нельзя переписать. Без этого `Rewrite`, который выучил текст и упал на проверке, оставлял его типы для следующих файлов.
- **Типизированные ошибки и предупреждения.** Синтаксическая ошибка — `*SyntaxError{Line, Column, Msg}` с позицией в переданном тексте; ошибка в теле функции или фрагменте PL/pgSQL переносится в текст по смещению начала тела (точно для `$$…$$` и `'…'` без экранирования, иначе — на начало литерала). Внутренние `parse.Error` и `plpgsql.Error` наружу не выходят. Каждая ошибка проверки оборачивает `ErrNotVerified`. Предупреждения — `[]Warning{Line, Message}`: строка места, если позиция есть, иначе первого токена оператора; строки тел пересчитываются в строки текста, если литерал хранит переводы строк тела как есть (`$$…$$`, `'…'`), иначе берётся строка литерала.
- **Настройки проверяются.** Имена в `ExcludeRelations` и `ExtensionObjects` — идентификаторы SQL, как в тексте; `New` отвергает то, что иначе молча не подействовало бы (пустое имя, имя со схемой, неизвестное расширение без имён, имена расширения, которое не включено, `Schema` вместе с `Placeholder`). В режиме метки текст, где метка уже есть, отвергается: `subst.Apply` заменил бы её и там, куда переписыватель её не ставил.
