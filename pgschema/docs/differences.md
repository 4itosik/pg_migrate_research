# Отличия от прототипа

Прототип `poc/pgquery` — эталон поведения переписывания: вывод `pgschema` должен совпадать с ним побайтно везде, где оба переписали. Здесь перечислены места, где это не так, и ошибки прототипа, которые найдены при сверке. Прототип не правится.

Каждое отличие — либо ошибка `pgschema`, и тогда её исправляют, либо осознанное улучшение: оно записывается сюда с причиной и подтверждается на живом PostgreSQL.

## Улучшения

Пока пусто. Известные ограничения прототипа, которые `pgschema` должна снять (README, §6 и `HANDOFF.md`):
- разбор PL/pgSQL без каталога: отказы на параметрах `refcursor`, на `$0` в полиморфных функциях и на элементе массива как цели `GET DIAGNOSTICS` ([ADR 0003](adr/0003-plpgsql.md));
- позиции имён в `DROP`, `COMMENT ON`, `CREATE FUNCTION`, `CREATE TYPE` и у функции триггера: прототип ищет их в токенах.

## Лексер: отличия libpg_query от сервера

Лексер сверяется с `Scan` из libpg_query. Там, где libpg_query расходится с настоящим сервером, поведение выбрано так.

| Вход | libpg_query | Сервер | Лексер |
|---|---|---|---|
| `'a' -- c⏎'b'` (строка, комментарий `--`, перевод строки, продолжение) | две строки `'a'` и `'b'` | одна строка `ab` (PostgreSQL 16.15, проверено) | как сервер: одна строка. Флаг `LibpgQueryCompat` воспроизводит libpg_query, им пользуется только сверка и считает такие входы отдельно (`*_deviations` в отчёте) |
| `$1a` | `PARAM` и `IDENT` | PostgreSQL 16.15 и `REL_17_STABLE`: ошибка «trailing junk after parameter»; 12 и 14 принимают | как libpg_query и старые серверы: `PARAM` и `IDENT`. В libpg_query из `pg_query_go` нет правила `param_junk`, оно появилось в свежих минорных версиях PostgreSQL |

Причина первого отличия: libpg_query правит `scan.l`, чтобы отдавать комментарии токенами, и после правки комментарий внутри разделителя строк уже не считается пробелом. `/* c */` между частями строки не склеивает их ни там, ни там.

## Парсер: отличия от дерева libpg_query

Деревья совпадают поле за полем, с позициями, на всех 188 760 операторах корпуса и регрессионных тестов PostgreSQL 12–16. Отличаются только вещи, которые дерево не показывает или показывает по-другому у эталона:

| Что | libpg_query | `internal/parse` |
|---|---|---|
| Позиции имён у `String` | нет | поле `Loc` у `String`: смещение имени в `DROP`, `COMMENT ON`, `CREATE FUNCTION`, `CREATE TYPE`, у функции триггера и везде, где имя стоит в списке. При сверке игнорируется |
| `FETCH ALL`, поле `howMany` | 2147483647: libpg_query собран под 32-разрядный WebAssembly, где `LONG_MAX` 32-битный | то же значение; на 64-разрядном сервере там 2^63−1. Для переписывания не важно |
| `NULL` у `char *` и пустая строка | proto не хранит пустые строки | не различаются. В C грамматика проверяет `$$ != NULL` для `SET NAMES ''`, `opt_encoding` и подобных: у нас пустая строка в таком месте даст ветку «нет значения». Это единственное известное поведение, которое зависит от различия; в регрессионных тестах не встречается |
| Невалидный UTF-8 во входе | отказ при записи protobuf, «string field contains invalid UTF-8» | отказ с текстом сервера «invalid byte sequence for encoding "UTF8": 0x…» до разбора, как `pg_verifymbstr`. 4 оператора `collate.windows.win1252.sql` |
| Предупреждения и подсказки (`WARNING`, `NOTICE`, `errhint`, `errdetail`) | не попадают в результат | не выдаются |
| Маркер параметра `$1` там, где PostgreSQL требует строковую константу | принимает: libpg_query правит `gram.y` (`makeParamRef`, `makeParamRefCast`), чтобы разбирать подготовленные запросы: `SELECT a $1`, `int $1`, `interval $1`, `CREATE ROLE r PASSWORD $1`, `SET search_path TO $1`, `SET SCHEMA $1`, `SET ROLE $1`, `SET SESSION AUTHORIZATION $1` | отвергает с синтаксической ошибкой у `$N`, как сервер (проверено: сервер не принимает `SELECT a $1`). В миграциях параметров нет: файл выполняется простым протоколом. Принятое множество совпадает с libpg_query на регрессионных тестах, но не на таких входах; сверка по мутациям (`TestParseMutations`) их не считает расхождением |

Тексты ошибок и позиции курсора совпадают на всех операторах регрессионных тестов, которые отвергают обе стороны (243–525 на версию), кроме четырёх операторов с невалидным UTF-8.

## Переписывание: улучшения относительно прототипа

Вывод побайтно совпадает с прототипом на 54 файлах корпуса и на всех операторах регрессионных тестов, которые переписал и он (42 787 из 42 798 на PostgreSQL 16; остальные 11 — ниже). Отличия, которые остались, это отказы прототипа и два места, где у нашего переписывания больше возможностей.

| Что | Прототип | Библиотека |
|---|---|---|
| Тела, которые libpg_query не компилирует, хотя сервер их принимает: `refcursor` как параметр, `FOR r IN c LOOP` по курсору без запроса | отказ «PL/pgSQL parse error» (8 тел в регрессионных тестах PostgreSQL 16) | переписываются: извлечение SQL (`internal/plpgsql`) не компилирует тело, а разбирает его по структуре. Тела, которые сервер отвергает при создании (повтор параметра, неверное число аргументов `RAISE`), тоже переписываются, и результат отвергается сервером так же, как исходный текст |
| `CASE x WHEN список THEN` | выражение списка в JSON — служебный текст, которого нет в теле; если в нём есть что квалифицировать, отказ «cannot locate» | список квалифицируется как `x IN (список)` по своим позициям |
| Цель присваивания `a[i = 1] := …` | первое `=` или `:=` в тексте, в том числе внутри индекса | первое вне скобок и квадратных скобок |
| Местоположение запроса в теле | поиск текста запроса в теле (с «слепыми» пробелами вместо `INTO`) | позиции из извлечения, текст не ищется |
| Проверка тела | повторный разбор оператора целиком | то же, плюс повторное извлечение из нового тела: те же фрагменты, режимы и объявления |
| Строка с именем отношения: `nextval(' s ')`, `$$s$$::regclass` | заменяет литерал целиком, пробелы по краям отбрасывает, кавычки заменяет на `'…'` | вставляет схему внутрь литерала перед именем (после пробелов), литерал остаётся как написан; целиком переписывает только литерал с экранированием или удвоенными кавычками (`E'\x74'`), и вставка тогда не чистая |

Остальные расхождения с прототипом на входах, которых нет в регрессионных тестах (нашла проверка свежим взглядом и фаззинг):

| Что | Прототип | Библиотека |
|---|---|---|
| Идентификатор длиннее 63 байт (`40 × 日` — 120 байт) | отказ: токен в тексте сравнивается с именем, которое PostgreSQL уже усёк до 63 байт | переписывает |
| Имя с Unicode-экранированием `U&"d\0061t"` | отказ: текст токена не равен имени | переписывает; результат проверяет повторный разбор |
| Нулевой байт во входе | переписывает текст до него (так видит его libpg_query, строка C кончается на нулевом байте), остаток не трогает, без ошибки | отказ с текстом сервера «invalid byte sequence for encoding "UTF8": 0x00» |
| `RETURNS TABLE (c тип)` с одним столбцом | отказ: позиция типа возврата указывает на `TABLE` | квалифицирует тип столбца, тип возврата берёт у столбца |
| Тело `'…'`, оканчивающееся на `$` | `$$…$$$`, результат не разбирается, отказ | выбирает тег, который закрывает литерал на месте (`$body0$…$body0$`) |
| Тип в объявлении, который не является именем типа (`m mood int`) | libpg_query принимает как текст типа, прототип переписывает, не трогая тип | отказ: сервер такую функцию не создаст |

Отказывают обе стороны на 3 операторах PostgreSQL 16 (в них SQL недопустим: `AS 'not even SQL'`, `select I fought the law`): сервер тоже не создаст такие функции.

Подтверждение на сервере: на корпусе PostgreSQL 12–16 проходят те же 22 сценария из 23, что у прототипа (сценарий 12 — динамический SQL, ожидаемое ограничение); `TestGolangMigrate` применяет корпус через golang-migrate (драйвер `pgx/v5`) и сравнивает `pg_dump` схемы с прямым переписыванием.

## Ошибки прототипа

Найдены при сверке; прототип (`poc/`) не менялся.

- Нулевой байт во входе: переписывает только часть текста до него и не сообщает об этом (`SELECT 1 \x00 FROM t` остаётся с `t` без схемы). Сервер такой текст не примет. Остальное — отказы, не неверный текст: идентификатор длиннее 63 байт, `RETURNS TABLE (c тип)` с одним столбцом, тело `'…'` с `$` в конце (таблица выше).
