## Этап 1. Лексер

Порог: токены и смещения совпадают с `Scan` из libpg_query на всех входах корпуса и регрессионных тестов PostgreSQL 12–16.

Порт `scan.l` (PostgreSQL 17) в `internal/lex`: все виды литералов (`E'…'` со всеми экранированиями и суррогатными парами, `U&'…'`, `$tag$…$tag$`, `B'…'`, `X'…'`, `N'…'`, числа с `_`, `0x`, `0o`, `0b`), вложенные комментарии, продолжение строк через перевод строки, ключевые слова из `kwlist.h` (491, с категориями и признаком `BARE_LABEL`), свёртка и усечение идентификаторов, тексты ошибок и позиции курсора. Таблицы токенов и ключевых слов генерирует `oracle/cmd/gentokens`: номера токенов те же, что у libpg_query.

Сверка (`oracle/lexer_test.go`) сравнивает номер токена, смещения, категорию ключевого слова, а для ошибок — текст сообщения и позицию курсора. Результаты в этой сессии, Go 1.26.1:

|---|---|---|
| Файлы корпуса, `setup.sql`, `check.sql` | 100 | 0 |
| Операторы регрессионных тестов PostgreSQL 12 / 13 / 14 / 15 / 16 | 32 267 / 35 005 / 38 052 / 41 598 / 43 323 | 0 / 0 / 0 / 0 / 0 |
| Токенов в них на PostgreSQL 16 | 615 286 | |

| Мутации реальных операторов PostgreSQL 16 | 20 000 (3 741 отвергнуто) | 0 |

Случайные входы нашли и заставили исправить: разбиение `{decinteger}{identifier}` по внутреннему подчёркиванию (`1_0$` — ошибка, а не число и `$`), границы текста в «at or near» (flex ставит NUL после текущего совпадения, и PostgreSQL печатает текст только до него). Отклонения libpg_query от сервера описаны в [docs/differences.md](docs/differences.md); в регрессионных тестах они не встречаются, в случайных входах — по 0–1 на сид.

Скорость: 1,64 мкс на оператор регрессионных тестов PostgreSQL 16, 47 МБ/с, 119 нс на токен, 0 аллокаций (`results/metrics.json`, `stage1.lexer.speed_pg16`). Сборка: самый тяжёлый пакет библиотеки (`internal/lex`) компилируется в 49 МБ, чистая сборка библиотеки 11 с (`build`).

Собственные тесты лексера в библиотеке: `internal/lex/lex_test.go`.

## Этап 2. Грамматика

Порог: на корпусе все деревья совпадают с libpg_query вместе с позициями; на регрессионных тестах 12–16 — не меньше 99,9%; каждый оператор, который парсер принимает, а libpg_query отвергает, объяснён.

Сделано: порт `gram.y` PostgreSQL 17 на goyacc ([ADR 0001](docs/adr/0001-parser-construction.md), [0002](docs/adr/0002-tree.md), [0004](docs/adr/0004-small-functions.md)):
- форк goyacc (`internal/tools/goyacc`): позиции `@N`, действия функциями через таблицу, `-recv`;
- дерево `internal/ast` генерируется из описания libpg_query (`oracle/cmd/genast`): 268 узлов, 69 перечислений;
- правила — `internal/parse/gram/*.y`, скопированы из `gram.y` скриптом `tools/gramskel.py`; 2 258 действий перенесены на Go вручную (одиннадцать кусков параллельными исполнителями по [руководству](../pgschema/internal/parse/gram/PORTING.md), остальное и слияние — лидом) и сверены деревом;
- лексер-обёртка `base_yylex` (просмотр вперёд, `U&`), порты вспомогательных функций `gram.y` и `makefuncs.c`.

## Этап 3. PL/pgSQL

Порог: на всех телах корпуса и регрессионных тестов, которые разбирает libpg_query, совпадают встроенные запросы, их режимы и номера строк; тела, на которых libpg_query падает по причинам из решения 3 ([ADR 0003](docs/adr/0003-plpgsql.md)), разбираются.

Результат: блоки, обработчики, метки, операторы с вложенностью, фрагменты SQL (позиции в теле, режим разбора, строка), объявления с типами и позициями имён, динамический SQL. ## Этап 4. Переписывание

Порог: корпус на PostgreSQL 12–16 — как у прототипа; регрессионные тесты — вывод побайтно совпадает с прототипом везде, где оба переписали; отказов не больше, чем у прототипа (11 на PostgreSQL 16); непроверенных результатов нет.

Сделано (корень модуля `pgschema`): правила прототипа на своём дереве — `walker.go` (обход, CTE, объекты DDL, литералы `regclass`), `functions.go` (SQL-тела, тела PL/pgSQL и `DO` через `internal/plpgsql`), `registry.go` (что создали миграции), `rewriter.go` (`New`, `Learn`, `Rewrite`, проверка), `edit.go`. `Rewrite` вставляет `schema.` в исходный текст, разбирает результат и сравнивает дерево с входным, где те же имена уже квалифицированы; тело PL/pgSQL проверяется ещё раз структурой. Любая неудача — ошибка, не текст.

Результаты (Go 1.26.1, `go test ./oracle` с `tools/env.sh N`, сервер PostgreSQL N):

## Этап 5. Для сервисов

Порог: метка и подстановка дают тот же текст, что прямое переписывание, для `auth`, `Auth`, `user`, `my schema` на корпусе и регрессионных тестах; подстановка отвергает `'` и `$`.

- `Options{Placeholder: true}` пишет метку `pgschema_placeholder`; пакет `subst` (только стандартная библиотека) заменяет её на имя схемы с кавычками по правилам `quote_identifier` (таблица зарезервированных слов генерируется из `kwlist.h`), `ValidSchema` отвергает пустое имя, длиннее 63 байт, `'`, `$`, `\` и управляющие символы.
- Сверка (`TestPlaceholder`): 42 849 текстов (54 файла корпуса и операторы регрессионных тестов PostgreSQL 16) × 4 имени — 0 различий; 3 текста отвергают обе стороны.
- CLI `cmd/pgschema rewrite`: каталог golang-migrate → каталог, `-placeholder`, `-exclude`, `-check` (сверяет каталог с тем, что записал бы; ненулевой код при расхождении, недостающем и лишнем файле), `-fail-on-warning`. Тесты: `cmd/pgschema/main_test.go`.
- `migratesrc.Wrap(src, schema)` — вложенный модуль (golang-migrate нужен только ему, [ADR 0005](docs/adr/0005-layout.md)): оборачивает `source.Driver`, подставляет схему в `ReadUp`/`ReadDown`. `TestGolangMigrate` применяет корпус настоящим golang-migrate на сервере и сравнивает `pg_dump` схемы с прямым переписыванием, затем `Down`.
