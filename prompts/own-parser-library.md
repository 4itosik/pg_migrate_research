# Библиотека квалификации схемы в миграциях PostgreSQL на собственном парсере

> Промпт для Claude Sonnet 5.5 (`claude-sonnet-5-5`) в агентной среде с терминалом и git, например в Claude Code. Агент запускается в корне этого репозитория: исследование, датасет и прототип лежат рядом, библиотека разрабатывается в каталоге `pgschema/`. Рекомендуемый уровень effort — `high` или `xhigh`. Задача на несколько месяцев и много сессий: промпт задаётся в начале каждой, состояние между сессиями хранится в `pgschema/PROGRESS.md` и `pgschema/NOTES.md`. Перед запуском укажи рабочую ветку.

## Зачем

Мы накатываем миграции PostgreSQL через golang-migrate в десятках Go-микросервисов. Подключение идёт через pgbouncer в transaction mode, поэтому `search_path` задать нельзя. Нужно по флагу и имени схемы добавлять схему к объектам в SQL-файлах миграций:

```sql
CREATE TABLE users (...)       -- было
CREATE TABLE auth.users (...)  -- стало
```

Исследование уже сделано. Прототип переписывания построен на libpg_query — парсере самого PostgreSQL, собранном в WebAssembly (`github.com/wasilibs/go-pgquery`). Он проверен на корпусе миграций и на регрессионных тестах PostgreSQL 12–16. Но у него есть цена. С wazero это холодный старт 1,5 с и до 280 МБ памяти на старте каждого процесса. Со сборкой через wasm2go — 7 МБ сгенерированного кода и около 1,2 ГБ памяти компилятора. Для десятков сервисов это дорого.

Твоя задача — написать библиотеку с нуля на собственном парсере PostgreSQL на чистом Go. libpg_query остаётся только эталоном в тестах. Библиотека должна переписывать миграции так же надёжно, как прототип: тот же результат, никакого непроверенного SQL. Но без WASM, без cgo и с лёгкой сборкой.

## Где работать

- Весь код, тесты и документация библиотеки — в `pgschema/`.
- Исследование только читаешь: `poc/`, `README.md`, `TASK.md`, `HANDOFF.md`, `DATASET.md`, `prompts/`. Нашёл ошибку в прототипе — запиши её в `pgschema/docs/differences.md`, прототип не правь. Единственное, что можно добавить вне `pgschema/`, — CI: `.github/workflows/pgschema.yml`.
- Модуль библиотеки не зависит от libpg_query, go-pgquery, wazero и модулей из `poc/`. Сверку держи в отдельном модуле `pgschema/oracle/` со своим `go.mod` и `replace`:
  - `../` — библиотека;
  - `../../poc/pgquery` — прототип, эталон переписывания;
  - `../../poc/harness` — стенд на живом PostgreSQL.

  Так `go.mod` библиотеки остаётся без лишних зависимостей, а `go test ./...` в `pgschema/` не тянет WASM. Вложенный модуль в `./...` родителя не входит.
- Данные бери по относительным путям, копировать их не нужно. Из `pgschema/oracle/`: корпус — `../../poc/corpus`, скрипты — `../../poc/get-regress.sh` и `../../poc/get-postgres.sh`.
- Отчёты стенда пиши в `pgschema/results/`. Стенд берёт каталоги из переменных `CORPUS_DIR` и `RESULTS_DIR`, эталонные схемы ищет в `$RESULTS_DIR/baseline-schema`. Создай их прогоном `TestBaseline` модуля `poc/harness` с тем же `RESULTS_DIR`: это не меняет файлы в `poc/`.

## Что сдать

1. Go-модуль `github.com/4itosik/pg_migrate_research/pgschema` в каталоге `pgschema/`, Go 1.25, собирается с `CGO_ENABLED=0`:
   - лексер PostgreSQL: токены с байтовыми смещениями и категориями ключевых слов;
   - парсер SQL: дерево с позициями узлов;
   - разбор PL/pgSQL в объёме, нужном для переписывания: встроенные SQL-операторы и выражения с точными смещениями, объявления переменных и их типы, признаки динамического SQL;
   - переписывание: правила прототипа и проверка результата повторным разбором;
   - режим метки: переписывание с меткой вместо схемы и подстановка схемы в отдельном пакете только на стандартной библиотеке;
   - CLI: переписать каталог миграций, режим проверки для CI;
   - обёртка над `source.Driver` golang-migrate, которая подставляет схему.
2. Тесты, замеры и CI (см. «Как проверять»).
3. Документация в `pgschema/`: `README.md` (использование, гарантии, ограничения), решения в `docs/adr/`, отличия от прототипа в `docs/differences.md`, `PROGRESS.md`.

Ориентир API. Его можно менять, если есть причина; запиши её в ADR.

```go
// Переписывание: при сборке или в CLI
rw, err := pgschema.New(pgschema.Options{Schema: "auth", ExcludeRelations: []string{"countries"}})
err = rw.Learn(upSQL)              // заранее по всем up-файлам: какие типы и функции созданы миграциями
out, warns, err := rw.Rewrite(sql) // только вставки "auth." в исходный текст; ошибка вместо непроверенного SQL

// В сервисе: без парсера, только стандартная библиотека
sql, err := subst.Apply(tmpl, "auth") // метка pgschema_placeholder -> схема
src = migratesrc.Wrap(src, "auth")    // source.Driver для golang-migrate
```

## Ограничения

- Чистый Go: `CGO_ENABLED=0`. В коде библиотеки нет WASM, wazero, wasm2go и кода, переведённого из C. libpg_query разрешён только в модуле сверки `pgschema/oracle/`, который сервисы не импортируют.
- Переписывание только вставляет текст в исходный SQL. SQL заново не генерируется: комментарии, форматирование и кавычки остаются как в оригинале.
- Непроверенного результата не бывает. Если вход не разобрался или повторный разбор результата не дал ожидаемое дерево, `Rewrite` возвращает ошибку.
- Пакет подстановки и обёртка для golang-migrate не тянут парсер.
- Зависимости рантайма — только стандартная библиотека. Исключение: если в ADR выберешь дерево из `pg_query_go` (см. ниже), то `google.golang.org/protobuf` и `github.com/pganalyze/pg_query_go/v6` без cgo.
- Бюджеты на 4 ядрах, Go 1.25:
  - первый разбор в процессе — не больше 5 мс;
  - разбор оператора в среднем по регрессионным тестам PostgreSQL 16 — не больше 20 мкс;
  - переписывание всего корпуса в одном процессе — не больше 0,1 с;
  - пиковая память компилятора на любой пакет — не больше 700 МБ, чистая сборка CLI — не больше 30 с;
  - бинарник CLI — не больше 15 МБ.

  Для сравнения из исследования: парсер pgplex/pgparser, сгенерированный goyacc из `gram.y`, компилируется за 8 с и 420 МБ. Компилятору Go нужно непропорционально много памяти на функции в десятки тысяч строк.
- Лицензии. Грамматика PostgreSQL распространяется под PostgreSQL License: сохраняй атрибуцию в портированных файлах. Чужие Go-порты (pgplex/pgparser, multigres) можно читать как справку, но код пишется с нуля.

## Решения до начала кода

Запиши их в `pgschema/docs/adr/` с обоснованием.

1. **Как строить парсер.** Рекомендую порт `gram.y` на goyacc (или на свой форк goyacc) с отслеживанием позиций: грамматика совпадает с PostgreSQL по построению, а расхождения ловит сверка. goyacc не умеет `@N`. Позицию токена можно класть в объединение значений, а для нетерминала брать позицию первого непустого символа правой части, как `YYLLOC_DEFAULT` в `gram.y`. Масштаб: в `gram.y` PostgreSQL 17 — 19 520 строк, 727 правил, около 3 400 альтернатив, позиции задаются в 625 местах. Рукописный рекурсивный спуск тоже допустим, если сверка покажет ту же точность.
2. **Каким будет дерево.**
   - Вариант А: типы `pg_query_go` (protobuf). Сверка с libpg_query сводится к `proto.Equal`, обход дерева из прототипа переносится почти без изменений. Цена — зависимость от protobuf и первый разбор медленнее из-за инициализации.
   - Вариант Б: свои структуры по `parsenodes.h` и `primnodes.h` плюс генерируемый конвертер для тестов.

   Выбери по замерам.
3. **Как разбирать PL/pgSQL.** Нужен не компилятор, а извлечение: операторы, их SQL-фрагменты с точными смещениями и режимом разбора (оператор, выражение, присваивание), объявления, динамический SQL. libpg_query компилирует PL/pgSQL без каталога и поэтому падает на параметрах `refcursor`, на `$0` в полиморфных функциях, на элементе массива в `GET DIAGNOSTICS` и на присваивании полю составной переменной. Свой разбор не должен зависеть от типов переменных.
4. **Как держать функции маленькими**, чтобы уложиться в бюджет памяти компилятора. Например, действия грамматики можно вынести в отдельные функции.

## Этапы

Каждый этап заканчивается так: проверки этапа зелёные, `pgschema/PROGRESS.md` обновлён с цифрами, изменения закоммичены и запушены в рабочую ветку. К следующему этапу переходи, когда порог текущего выполнен. Если порог недостижим, запиши в `PROGRESS.md`, почему, и что предлагаешь.

| Этап | Результат | Порог приёмки |
|---|---|---|
| 0. Основа | Модуль сверки `pgschema/oracle/`, подключение стенда и датасета, CI, отчёт метрик, ADR по решениям 1–4 | `go test ./...` зелёный в `pgschema/` и в `pgschema/oracle/`, отчёт метрик строится |
| 1. Лексер | Порт `scan.l`: все виды литералов (`E'…'`, `U&'…'`, `$tag$…$tag$`, `B'…'`, `X'…'`, числа с `_` и `0x`), вложенные комментарии, ключевые слова из `kwlist.h` с категориями | токены и смещения совпадают с `Scan` из libpg_query на всех входах корпуса и регрессионных тестов PostgreSQL 12–16 |
| 2. Грамматика | Порт `gram.y` PostgreSQL 17 с позициями | корпус: все деревья совпадают с libpg_query, вместе с позициями. Регрессионные тесты 12–16: совпадает не меньше 99,9% операторов, остальные перечислены с причинами. Каждый оператор, который парсер принимает, а libpg_query отвергает, объяснён |
| 3. PL/pgSQL | Извлечение SQL из тел функций и DO-блоков | на всех телах корпуса и регрессионных тестов, которые разбирает libpg_query, совпадают встроенные запросы, их режимы и номера строк. Тела, на которых libpg_query падает по причинам из решения 3, разбираются |
| 4. Переписывание | Правила прототипа на своём парсере, проверка повторным разбором, предупреждения | корпус на PostgreSQL 12–16 — как у прототипа: проходят все сценарии, кроме 12 (динамический SQL, ожидается предупреждение). Регрессионные тесты: вывод побайтно совпадает с прототипом везде, где оба переписали; отказов не больше, чем у прототипа (11 на PostgreSQL 16); непроверенных результатов нет |
| 5. Для сервисов | Режим метки, пакет подстановки, CLI с режимом проверки, обёртка для golang-migrate | метка и подстановка дают тот же текст, что прямое переписывание, для схем `auth`, `Auth`, `user` и `my schema` на корпусе и регрессионных тестах. Подстановка отвергает имена схем с `'` и `$` |
| 6. Доводка | Фаззинг лексера, парсера и переписывания со сверкой против libpg_query, бюджеты, документация, CI на PostgreSQL 12–16 | фаззинг без падений и необъяснённых расхождений, бюджеты выполнены, README описывает гарантии и ограничения |

Не пытайся сделать всё за одну сессию. Заканчивай сессию на рабочем состоянии с записанным прогрессом.

## Как проверять

- **Эталон разбора** — libpg_query через go-pgquery, только в модуле сверки. Сравнивай не «разобралось или нет», а деревья целиком, вместе с позициями.
- **Эталон переписывания** — прототип `poc/pgquery`: подключи его в модуле сверки и сравнивай вывод на тех же входах. Любое расхождение с ним — либо ошибка, либо осознанное улучшение. Улучшения перечисляй в `pgschema/docs/differences.md` и подтверждай на живом PostgreSQL.
- **Данные** описаны в `DATASET.md`:
  - корпус — `poc/corpus`;
  - регрессионные тесты PostgreSQL качает `poc/get-regress.sh`;
  - серверы PostgreSQL 12–16 качает `poc/get-postgres.sh`. Он берёт сборки из Maven Central, потому что `apt.postgresql.org` в облачных окружениях часто закрыт.
- **Стенд** `poc/harness` подключается через адаптер с двумя методами, `Learn` и `Rewrite`. Пример адаптера — `poc/pgquery/corpus_test.go`.
- **Регрессионные тесты** содержат намеренно неверный SQL. Считай только операторы, которые принимает libpg_query, а несовпадения разбирай по классам.
- **Метрики** пиши в JSON-отчёт: доля совпадений по этапам, отказы, скорость, память компилятора, размер бинарника. Память компилятора меряй через `-toolexec`, пример — `poc/pgquery/wasm2go/maxrss`.
- **Ловушки из исследования** должны быть в тестах:
  - имя в `FOR UPDATE OF t` остаётся без схемы;
  - не квалифицируются имена CTE в области видимости, временные таблицы, transition tables триггеров (`REFERENCING NEW TABLE AS x`), `pg_*` и `information_schema`;
  - типы и функции квалифицируются, только если их создали миграции. Встроенные и объекты расширений не трогаются;
  - схема ставится и внутрь строк: `nextval('seq')`, `'t'::regclass`, `pg_get_serial_sequence('t', …)`, `to_regclass('t')`;
  - изменённое тело функции в `'…'` переводится в долларовые кавычки, `E'…'` переквотируется;
  - у части имён в дереве PostgreSQL нет позиций: в `DROP`, `COMMENT ON`, `CREATE FUNCTION`, `CREATE TYPE`, функция триггера. Прототип ищет их в токенах; свой парсер может отдавать позиции и для них;
  - ANTLR-грамматика из исследования разбирала `ALTER TABLE t ADD CONSTRAINT c CHECK (…)` как добавление колонки `CONSTRAINT` типа `c`, а `FROM unnest((SELECT …))` — как таблицу `unnest`;
  - динамический SQL (`EXECUTE`), поиск в каталогах по имени, `current_schema()`, `SET search_path` и `CREATE EXTENSION` без `SCHEMA` дают только предупреждения.

## Как работать

- В начале каждой сессии прочитай `pgschema/PROGRESS.md` и `pgschema/NOTES.md`, в конце обнови их.
- `pgschema/NOTES.md` — память между сессиями. Один урок — один пункт, сверху строка с сутью. Записывай подтверждённые подходы и исправления вместе с причиной. Не дублируй то, что уже есть в коде, ADR или истории git. Заметки, которые оказались неверными, удаляй.
- Сначала добивайся совпадения на корпусе, потом расширяй на регрессионные тесты.
- Коммить часто и маленькими шагами в рабочую ветку и пушь. Ветка всегда зелёная.
- После каждого значимого изменения прогоняй сверку этапа. В конце этапа проверь результат свежим взглядом: субагентом без твоего контекста, против этого промпта и прототипа, если субагенты доступны.
- Перед отчётом о прогрессе сверь каждое утверждение с выводом команды из этой сессии. Если тесты падают — так и напиши, с выводом. Если шаг пропущен — так и напиши.
- Работай автономно: обратимые действия, которые следуют из задачи, делай без вопросов. Спрашивай только о том, что меняет требования (ослабить порог или бюджет, убрать возможность), или когда нужен доступ, которого нет.
- Не добавляй возможности и абстракции сверх задачи. Не обрабатывай ситуации, которые не могут произойти.
- Код, комментарии и сообщения коммитов — на английском. Документация — на русском, как в исследовании.
- Итоговое сообщение сессии начинай с результата: что сделано и какие цифры. Затем — что мешает и что нужно от человека.

## Вне скоупа

Опиши в `pgschema/README.md` как ограничения, но не исправляй:
- golang-migrate берёт `pg_advisory_lock` — блокировку уровня сессии, ненадёжную за pgbouncer в transaction mode;
- схему таблицы `schema_migrations` golang-migrate берёт из `CURRENT_SCHEMA()`.
